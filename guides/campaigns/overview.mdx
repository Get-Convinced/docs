Campaign mode adds account context to a website agent. A visitor arrives with `?c=<token>`, and the backend resolves that token within the widget's organization. Use it for account-based outreach or a dedicated account page. A normal website SDK integration does not require campaigns; begin with [SDK overview](/guides/widget-sdk/overview).

## Campaign vs. target

| Concept | Meaning |
| --- | --- |
| Campaign | A group of target records, identified by an organization-scoped slug |
| Target | An account record containing structured intel, a token, and enrichment state |
| Widget token | The target identifier supplied as `?c=<token>`; it is not the campaign slug or a secret API credential |

Tokens are unique within an organization. Reusing a token under another campaign updates the same target and moves its campaign assignment. It does not produce a duplicate target or a `409` conflict. Use separate tokens when the records need to remain separate.

## How the widget uses context

The session personalization includes the company profile, up to six pain points, suggested customer proof, and stored crawled-page excerpts. The surrounding voice or chat integration must actually apply that context; for the SDK, follow [campaign sessions](/guides/widget-sdk/campaigns).

Campaign context guides model behavior. It does not guarantee particular wording, prevent all unsupported claims, or identify the person holding the link. Test the conversation with your own content.

A personal link (`pid`) has precedence over a campaign token when both resolve. A missing or unusable campaign record falls back to a generic session. Check `widgetReady` before sharing the link.

## The two integration modes

| Mode | Send | Initial state | Next step |
| --- | --- | --- | --- |
| Partner intel | `intel` and `enrich: false` | `skipped` | Read GET and confirm `widgetReady` |
| Auto-enrich | `rawResearch`, optional `links`/`additionalContext`, and `enrich: true` | `pending` | Poll GET until ready or failed |

When a valid `intel` object is supplied, it takes precedence and synthesis is skipped even if research or `enrich: true` is also present. Without intel, `enrich: false` stores an unready pending row without starting synthesis. Choose one clear mode in your integration.

## The lifecycle

| State | Meaning |
| --- | --- |
| `pending` | Stored, but enrichment has not completed; this does not guarantee a worker was started |
| `running` | Enrichment is in progress |
| `done` | Enrichment completed |
| `failed` | Enrichment failed; inspect `enrichmentError` |
| `skipped` | Structured partner intel was accepted, with no synthesis |

The GET response's `widgetReady` is true when the campaign is active, intel is present, and status is `done` or `skipped`. Upsert responses do not contain that field. See [the widgetReady gate](/guides/campaigns/widget-embedding#the-widgetready-gate).

To correct or retry a target, POST its full desired record to the same endpoint and token. This replaces fields and resets enrichment state. It does not cancel an already-running provider request; avoid concurrent writes to one target.

## What campaign data does not change

Campaign upserts do not edit the saved Convinced system prompt or opening message. Use [agent administration](/guides/widget-sdk/agent-prompts) for persistent agent settings.

`additionalContext` is stored and used during auto-enrichment. It is not currently appended verbatim to the live session prompt. For structured partner intel, put account facts into the supported intel fields rather than relying on `additionalContext` as a runtime instruction.
