SDK 0.1.8 offers optional full-duplex voice through OpenAI `gpt-live-1` and WebRTC. Live handles greetings, conversational clarifications, and explanations supported by its current page or reference context directly. It delegates missing facts and requests that need slides or tools to the backend agent in the existing Convinced session. The backend agent can continue through multiple knowledge and browser steps for one request.

<Warning>
  Read the [availability and validation status](/guides/widget-sdk/overview#availability-and-validation-status) before enabling voice for customers. Full-duplex protocol support is not a claim that your deployed audio flow has passed acceptance.
</Warning>

## Channel contract

| Action | Result |
| --- | --- |
| Initialize chat only | Creates a Convinced backend agent conversation; creates no Live session |
| Start voice | Adds a Live WebRTC session to the existing conversation |
| Greet or clarify conversationally | Live responds directly without a backend agent round trip |
| Ask a factual question | Live can explain facts already supplied in its reference or page context; missing information delegates to the backend agent |
| Request a slide or page action | Live delegates the request to the backend agent, including recent Live-native context |
| Type while voice is active | The backend agent answers in the same conversation; a new typed turn stops unfinished delegated work, and Live receives a short briefing for speech |
| End or disable voice | Closes audio; chat stays active |
| End the SDK session | Ends the canonical conversation and any active Live transport |

Convinced owns the prompts and provider configuration for both models. The backend agent handles grounded business answers, rich content, and tool decisions. `gpt-live-1` handles conversation, listening, interruption, and speech delivery; it delegates actions and facts beyond its supplied evidence.

## Start from a user gesture

```ts
const live = client.createLiveController()

enableVoiceButton.addEventListener('click', async () => {
  await live.start({ startMuted: false })
})

disableVoiceButton.addEventListener('click', async () => {
  await live.end()
  // client remains ready for typed turns
})
```

The SDK sends a WebRTC offer to Convinced. The backend authenticates the current widget session, loads its `AgentDeployment`, and creates the Live session with the server's OpenAI key. The browser receives the WebRTC answer, never the key. Browser tools stay on the canonical backend agent chat path; they are not registered with Live.

`live.liveSessionId` is the runtime Live transport handle received during startup. You do not provision or configure it. Use the Convinced session ID for conversation history, identity, tool results, and analytics; the Live handle does not replace it.

## Controls and context

```ts
live.setMuted(true)
live.setMuted(false)

live.sendContextualUpdate(
  `Current page: ${document.title} (${location.href})`,
  'current-page',
)
```

Context updates are untrusted observations. They do not replace the saved Convinced prompt or grant tool permissions.

Supply concise website-authored capability descriptions when Live needs to explain their benefits during a delegated action. Label that background reference separately from the current visible view. Keep authored limitations, exclude private visitor data, and use verified receipts to establish what has actually opened.

### Background available at startup

Live receives startup input immediately; context appended during a call is delivered gradually. Use startup background for facts the assistant needs from its first exchange, and later updates for changes to the current page. An append acknowledgment does not prove that the model has used the whole update. See [OpenAI's Live conversation guide](https://developers.openai.com/api/docs/guides/live-conversations).

The matching Convinced backend accepts optional `context` alongside `sdp` in the authenticated `POST /api/widget/{orgSlug}/session/{sessionId}/live` JSON body. It seeds that text as explicitly untrusted background in Live's startup input. The context must be a string of at most 8 KiB in UTF-8. It cannot change the saved prompt, select a model, authorize tools, or establish what is visibly open.

SDK 0.1.8 sends `{sdp}` on that route. Its `live.start({context})` option sends an after-connect update; it does not seed startup input. To use the optional backend field with this release, a host-supplied `fetch` adapter must add it only to its own Live startup request, preserving the SDK's session authorization, headers, and abort signal. Ordinary SDK requests remain compatible without an adapter. Do not send provider credentials or copy a request to another origin.

The backend keeps recent conversation within its existing message bounds and can prune older history to make room for background. If the background would crowd out the newest exchange, it is omitted and the existing history behavior is retained. A successful Live response does not confirm that optional background was included. Keep startup facts compact and still support later current-page updates.

## Live payload limits

SDK 0.1.8 keeps each commentary or thinking append within a conservative 450-byte UTF-8 cap, below GPT Live's 500-token per-append limit.

For a grounded answer, the backend agent can return a short, verified voice briefing alongside its full written answer. The SDK sends that briefing to Live for natural speech. If no briefing arrives, the SDK uses a complete sentence from the written answer after removing media directives and Markdown links; it does not splice the beginning and end of a long answer together. Full text and structured slide or video content remain available through the client.

Page/context updates keep the existing 8 KiB input limit. `live.sendContextualUpdate()` splits accepted context into ordered thinking appends of at most 450 UTF-8 bytes each, including any context-ID prefix in the first append. Inputs above 8 KiB are rejected.

Keep page context concise and factual. After upgrading, verify a long grounded answer and a long page update on your deployed page. Continue handling Live connection and provider errors through the normal error events.

## Delegation and tools

Live delegates missing facts, slides, and tools. A greeting, conversational clarification, or explanation supported by supplied evidence can stay in Live. If the backend agent requests a browser tool, Convinced pauses the agent run and keeps its state on the server. The SDK runs the local registry checks and handler, then returns an opaque signed continuation with the result. Convinced verifies the call, accepts the continuation once, and resumes the backend agent with the browser observation. Live receives a short briefing of the result for speech; the full answer remains in the client.

Interrupting speech is separate from canceling a task. Live should handle a backchannel or “stop talking” without starting a new backend request. A clear correction to the work should delegate the revised request; the SDK stops the superseded delegated turn before later browser tools run. Typed input submitted during delegated work also takes precedence. A browser action that already completed cannot be undone by cancellation, so the next answer must use the actual page state.

This keeps tool authorization, form handling, page actions, slides, and knowledge consistent across input modes.

## Responsiveness and recovery

Live can explain relevant facts already in its page or reference context while a page action runs. A visitor's role or broad goal can be enough to show a supported category or scope overview; explain a grounded benefit before asking for more details. Use the last verified overview for a continuation instead of presenting it again. Claim navigation only after a successful host receipt confirms the destination; a tool request or a progress message does not confirm movement.

Public page text and headings can include off-screen sections. They do not establish the current viewport, a completed navigation, or that a requested section is absent. A fresh verified action receipt supersedes earlier page observations; explain the content it confirms is now shown.

The current hosted backend uses a shared 30-second budget for each agent run, including a resumed run, in both voice and text. The budget starts at the agent runner after request preparation. Browser actions and preparation take additional time, and a multi-step request can contain several runs; this is not an end-to-end response guarantee. If a run exceeds its budget, the backend finishes the turn with a recoverable answer and, for voice, a short spoken briefing.

A completed page action remains completed if the follow-up answer times out. Keep its verified receipt visible and report the answer failure separately. Show failed or ambiguous action receipts promptly, even while an answer is pending. Do not automatically repeat a consequential action when its outcome is unknown. Let the visitor retry or refine the request, and retain typed chat as a fallback.

Measure time to useful speech separately from time to a verified page action. An acknowledgment, a saved greeting, an append acknowledgment, or received audio packets alone does not establish either result. See [Analytics and testing](/guides/widget-sdk/analytics-and-testing).

## Carry clarification into the next request

For example, Live can respond to “Help me understand this” with “Which workflow would you like to explore?” The SDK adds that completed user/assistant pair to the shared client history. If the visitor then says or types “Dispatch planning,” the backend agent can use the preceding clarification instead of treating the short answer as an isolated question.

Completed Live-native user/assistant pairs are added to `client.state.messages` within the SDK's text and history limits. Client state subscribers are notified, but the SDK does not emit duplicate client `message` events for these pairs. Render the shared conversation from state; Live's `onMessage`, `message`, and `message_delta` events remain available for captions. Do not replay captions through `client.sendMessage()`.

By default, `client.endSession()` includes the completed pairs in its `/session/end` payload. This covers completed exchanges, not every partial transcript fragment. It does not promise restoration across page reloads or Live reconnections. See [Conversation sessions](/guides/widget-sdk/sessions#persisted-history).

The behavior requires the matching Convinced Live configuration as well as SDK 0.1.8. Start a fresh Live session after upgrading. Test a greeting and clarification, a spoken request that uses a slide or page tool, a speech backchannel, and a clear mid-task correction on your deployed page.

## Render voice state

```ts
live.on('state', state => {
  renderVoiceStatus(state.status)
  renderMuted(state.muted)
  renderMode(state.mode) // listening, speaking, or overlap
})

live.on('error', error => {
  showVoiceError(error.message)
  showChatComposer() // chat remains available
})
```

Use `live.subscribe(listener)` when the renderer needs an immediate state snapshot plus later state updates. Use `live.on(event, listener)` for named events. Both return an unsubscribe function; the Live controller does not expose `once()` or `off()`.

Request microphone access only after a clear visitor action. Show listening and speaking state, support interruption, and provide an obvious way to stop audio.

## Known issue: false input during silence

A local browser session produced repeated caller text while the visitor was silent; the visitor reported continued text and interruptions while muted. Ending the voice session stopped it. The root cause remains unresolved. Later synthetic tests reproduced caller fragments before a prerecorded utterance played, while only digital silence was being sent. A matched mute acknowledgement stopped further caller fragments in those tests; this does not establish physical-microphone acceptance. Audio packets alone do not establish audible speech.

If this occurs, end voice with `await live.end()` and continue through typed chat. Do not present a mute icon as proof that the full input path is working. Preserve the Convinced session identifier for diagnosis; do not publish transcripts or record microphone audio without the visitor's permission.

SDK 0.1.8 keeps overlapping speakers' transcript buffers independent, ignores exact replayed event IDs while preserving intentional repeated words, and correlates mute acknowledgements with the latest request. These fixes do not prove the false-input issue is fixed.

## Incremental context and page snapshots

The SDK/backend pair can forward bounded, verified page findings before the backend agent's final answer, allowing Live to explain new facts while work continues. Live owns the spoken wording; private reasoning and unverified action claims must not be streamed as facts. This is not general token-by-token speech of every backend delta.

A screenshot method remains experimental; see [page-aware guides](/guides/widget-sdk/page-aware-guides#screen-inspection-experimental). A model can request inspection through a host tool, but it cannot grant browser capture permission. Structured page state is not pixel vision.

## Page evidence during speech

SDK 0.1.8 can supply compact current-page observations to Live directly, so it can explain known page facts while a backend action runs. Facts outside that evidence or an action can still delegate to the shared backend agent. Coherent verified findings use `session.commentary.append` with the current delegation ID; quiet context uses `session.thinking.append`. An append acknowledgement confirms context injection, not completed playback. Keep native Live explanations and backend briefings from repeating the same explanation.

This uses the Live protocol, not `response.create`. The Convinced backend uses GPT-6.1 Sol with low reasoning. See [availability](/guides/widget-sdk/overview#availability-and-validation-status).
