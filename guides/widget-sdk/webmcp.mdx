WebMCP lets a website expose structured JavaScript tools to agents. The SDK maps WebMCP to `ClientToolRegistry`; it does not create a second execution or authorization system.

<Warning>
  WebMCP is an evolving Community Group draft. Feature-detect it, choose the browser's supported argument encoding deliberately, and keep direct registry tools available when WebMCP is absent.
</Warning>

## Consume same-origin WebMCP tools

Use `getWebMcpModelContext()` to detect `document.modelContext` and the legacy `navigator.modelContext` shape. Pass the model context, host-selected origin, and authorizer to `createWebMcpBridge()`. Set the argument encoding explicitly for the browser you tested; the SDK defaults to JSON-string encoding when omitted.

```ts
import {
  ClientToolRegistry,
  createWebMcpBridge,
  getWebMcpModelContext,
} from '@convinced/widget-sdk'

const tools = new ClientToolRegistry()
const modelContext = getWebMcpModelContext()

const webmcp = modelContext
  ? createWebMcpBridge({
      modelContext,
      origin: window.location.origin,
      // Chrome <=154 uses JSON strings. Use 'object' only after verifying the
      // newer browser API; never retry a mutation with another encoding.
      argumentEncoding: 'json-string',
      authorize: async (tool, input) => {
        return showWebsiteToolConsent({ tool, input })
      },
    })
  : null

if (webmcp) tools.registerMany(webmcp.tools)
```

The bridge registers two fixed client tools: `host_webmcp_list_tools` and `host_webmcp_execute_tool`. Discovery returns opaque handles. Handles expire when the browser reports a tool change or when the bridge is disposed. Only same-origin tools are exposed.

Browser names, descriptions, schemas, annotations, and results are untrusted data. The mandatory `authorize(tool, input)` callback runs for the actual discovered tool on every execution. An annotation never grants permission.

Dispose the bridge when its owning route or integration unmounts:

```ts
webmcp?.dispose()
```

## Publish the registry to browser agents

`client.publishToolsToWebMcp()` publishes the client's existing registry, session context, and authorization policy without duplicating handlers. It returns an object with `ready` and `dispose`, or `null` when WebMCP is unavailable.

You can publish the registry before initializing the SDK client. Initialize the client before invoking consent-gated host actions: session-scoped consent requires an active SDK session, so deny those actions until a session is active. Keep the normal consent prompt visible to the visitor when a tool requires approval.

```ts
const published = client.publishToolsToWebMcp()
await published?.ready

// On route or integration teardown:
published?.dispose()
```

If any registration fails, `ready` rejects and the publisher aborts the registration lifecycle. Always await it before claiming that tools are available.

`publishRegistryToWebMcp()` is available when a host intentionally manages the registry execution context and authorization outside `ConvincedClient`.

## One governed execution path

Whether a tool was registered directly, adapted from MCP, or discovered through WebMCP, requests that need a browser tool use the same `gpt-6-luna` flow, whether they begin as typed input or delegated speech:

1. `gpt-6-luna` requests a named browser tool.
2. Convinced pauses the canonical turn and returns an opaque signed continuation plus the exact calls.
3. The SDK checks each call against the local registry, schema, limits, timeout, and host authorization.
4. `ClientToolRegistry` runs the registered `handler` once.
5. The SDK returns the result and opaque continuation to Convinced.
6. The backend verifies the signature, organization, session, turn, call IDs, tool names, arguments, expiry, and call count before resuming `gpt-6-luna`.
7. If Live is connected, `gpt-live-1` receives the backend's short verified voice briefing when available, or a bounded complete-sentence fallback. The full result remains in the client; see [Live payload limits](/guides/widget-sdk/voice#live-payload-limits).

The browser does not verify the server signature itself. It treats the continuation as opaque and cannot mint, alter, or reuse it for another turn.

Do not expose prompt administration, provider keys, unrestricted authenticated fetch, arbitrary DOM selectors, or destructive actions without fresh confirmation.

## Page visuals and screen inspection

Register page-owned navigation, selection and simulator actions when the website itself is the demonstration. WebMCP does not require slides and does not automatically discover every website capability: the host must implement and expose those actions.

A screenshot request is another bounded host capability, not a browser permission grant. Keep screen sharing under a visitor-controlled gesture, return a permission-required result when needed, and never label structured page state as a captured image. See [page-aware guides](/guides/widget-sdk/page-aware-guides#screen-inspection-experimental) for the local experimental path.
